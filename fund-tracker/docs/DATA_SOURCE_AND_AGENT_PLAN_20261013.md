## 先看结论

1. **旧天天基金 `fundgz` 接口已失效；换代理、HTTP/HTTPS 或仅升级 SDK 不能恢复它。** 本次依据官方 H5 请求契约接入 `FundValuationLast`。新接口能恢复部分指数/联接基金估值，但一些主动基金的估值字段为空，不是全覆盖替代品。接口变更也有[上游项目的一手故障记录](https://github.com/LeekHub/leek-fund/issues/677)，本项目结论以实际响应为准。
2. **新浪提供了本批主动基金/QDII 的有效估值备用，不应继续声称没有免费替代路径。** 29/30 是新增样本的当次源端估值覆盖；旧 27/28 有效报价包含正式净值，两种数字不可直接混算。货币基金收益继续排除出单位净值计价，所有样本比例均不代表全市场或长期可用率。
3. **已按用户选择实现：天天估值 → 新浪估值 → 有真实行情依据的推算 → 暂无估值；只有收盘后且当日正式净值已公布才自动显示净值，旧净值可手动查询。** 推算使用简短蓝色标记，完整披露日、行情时刻和假设仍保留；没有估值时不自动用旧净值或成本价补齐。
4. **建议选择性重构数据核心，不建议推倒重写 Vue、持仓及 SQLite。** 主要风险是数据口径与时效、跨日基准对齐、重复选择逻辑，而非技术栈。先固定数据契约，再把同一核心提供给 HTTP、CLI/MCP 和薄 skill，比整套应用重写更直接服务于后续目标。
5. **本次没有移植第三方代码、没有安装 MCP/智能体框架，也没有接入收费源。** 下列候选只供用户评估。免费公开接口没有已验证的全基金实时估值保障；收费产品也必须先用实际代码试查，不按宣传推定覆盖。

## 数据口径先分清

| 对象 | 含义与单位 | 不能混同的对象 |
|---|---|---|
| 单位净值 NAV | 一份基金份额对应的资产净值；人民币份额通常元/份，按净值日公布 | 累计净值、场内成交价格、万份收益 |
| 累计净值 ACCNAV | 纳入历史分红等因素的披露指标，通常同为元/份 | 当前份额价值；其比值也不能无条件当分红再投收益 |
| 源端估值 | 数据源提供的盘中估算值及其观测时刻，非基金正式公布净值 | 官方净值；“源端直接提供”不等于“基金公司正式认证” |
| 本项目推测 | 用披露持仓或关联标的真实行情，对最新公布 NAV 外推 | 数据源直接估值、全仓计价、保证精度的预测 |
| ETF/LOF 场内价格 | 交易所成交报价，有溢价/折价和流动性影响 | NAV/IOPV；即使查询到也不能直接替代场外基金净值 |
| 来源日增长率 | 来源按其口径给出的净值日涨跌百分比；本次用于链乘收益 | 简单累计净值比；缺失时价格变动口径会标注，非无条件总收益 |
| 货币基金万份收益/七日年化 | 每万份一天的收益/七天收益的年化指标 | 单位净值，不能拿 `0.2241` 等收益数值给份额计价 |

本次发现 efinance **0.5.8** 的 `get_realtime_increase_rate` 将 `ACCNAV` 映射到名为“最新净值”的列：样本 `161725` 的 NAV 为 **0.5338**，ACCNAV 为 **2.2499**，后者约为前者 **4.21 倍**。这是实际计价错误，不是四舍五入差异。生产链已去掉该路径，移动端备用接口直接读取 NAV；没有修改安装环境中的 efinance 源码。

## 架构取舍与后续优先级

| 路径 | 收益与代价 | 建议 |
|---|---|---|
| 只替换一个 URL | 恢复部分源端估值，但累计净值计价、前端补造、收益口径错误继续存在 | 不够，已实施必要的连带修复 |
| 选择性重构数据核心 | 保留应用及用户数据；报价/历史/统计规则可单独测试、跨 UI 和模型复用；迁移边界清楚 | **推荐**，本次已拆出显示选择与历史规范化，下一步独立无 UI 核心 |
| 彻底重写应用 | UI/持仓/导入迁移与数据兼容成本高，仍需同样修复上游问题；没有现有证据表明收益覆盖风险 | 暂不推荐；只有核心解耦仍被既有代码严重阻碍时再评估 |

当前仍值得解决的问题，不伪装成全部已修完：

- **P1 跨市场时间轴与推测验证**：当前只有上海交易时段及基础 HK/US 时区检查，不是完整交易所日历。须对齐基金 NAV 日、底层证券交易日和汇率，避免拿昨日海外涨跌或单日变动补多日 NAV 缺口。建立只使用当时已披露持仓的回测，按基金类型统计误差分位数、偏差和覆盖率；无证据时不输出假置信度。
- **P1 无 UI 数据契约与测试隔离**：`FundService` 仍混合搜索、筛选、推测和比较；服务包导入还会触发数据库初始化日志。把只读公共数据核心从 FastAPI/SQLAlchemy/用户持仓中解耦，而不是增加更多转发类。一次采集、一份 snapshot、多接口消费。
- **P1 历史收益契约完整性**：图表值已统一，对比区间收益已由后端按日历计算并保留起止日；统计使用可用全历史，图表 range 只控制绘图窗口。后续要持久保存来源、收益口径、分红/拆分及修订信息，识别历史缺口；海外日历、货币和年化分母须显式。不能把价格变动自动宣称为分红再投总收益。
- **P2 原基准工具统一**：旧 `run_all_tests.py` 仍是库级探索工具，混合 LOF 成交价、净值和累计净值，旧分数不能用来选择实时供应商。下一步复用当前数据契约，按 data_kind/nav_date/as_of 分组比较，而不是再维护一套生产逻辑。
- **P2 网络与可观测性**：保留 SQLite/内存缓存；先加同查询请求合并、共享并发预算、结构化业务错误和按能力的健康检查。小规模时不要为了“可靠”先引入 Redis、消息队列和大量熔断器。现有 `/health` 主要验证应用/DB/调度器，不等于数据源或估值覆盖健康。
- **P2 前端状态**：仍有前端缓存、服务缓存及组合快照多层；以快照 ID/真实时间解决一致性。持仓 API 的成功空列表与本地待同步操作还需明确区分，避免保留幽灵持仓。ECharts/Element Plus 按需加载可随后优化，不阻挡数据核心交付。
- **发布前安全门槛**：公共只读查询与持仓写入/截图 AI 密钥隔离。当前应保持回环地址；远程 HTTP/MCP 发布前再加认证、授权、配额和秘密存储。CORS 或 MCP 的只读注解不等于访问控制。

## 将能力提供给任意接入模型的路线

MCP 是模型与工具宿主交换工具定义/调用结果的协议；skill 是可发现的操作说明及资源。**单个 skill 文本不能让没有网络/工具执行能力的模型自行获得基金服务。** 应让数据核心独立于具体模型，宿主通过 MCP、OpenAPI/function tools 或受控 CLI 执行同一能力，skill 只教模型如何选口径和解释证据。[MCP 工具规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)、[Agent Skills 规范](https://agentskills.io/specification)。

建议目标结构（尚未创建新服务/skill）：

```text
真实上游适配器 + 能力/授权信息
            ↓
无 UI 的 FundData 核心：snapshot / history / deterministic statistics
            ↓
同一契约 → REST/OpenAPI · CLI JSON · MCP（stdio 或受控 HTTP）
            ↓
薄 skill：选代码、选口径、处理缺失、引用来源、解释结果
            ↓
任意具有相应工具宿主的模型；不绑定单一模型供应商
```

核心应暴露少量完整能力，而不是给模型几十个底层供应商函数：

| 建议工具 | 输入重点 | 输出/约束 |
|---|---|---|
| `search_funds` | 名称/代码、类型、limit | 候选及匹配依据；重名 A/C 份额不擅自替换 |
| `get_fund_snapshot` / batch | 代码、auto/provider/nav、可否推测、最大时效 | 类型化 snapshot + actual as_of、fetched_at、NAV 日、来源/上游、币种、基准日、推测依据/缺失原因 |
| `get_fund_history` | 明确起止日、单位/累计/收益口径、分页 | 可追溯序列；当前纯净值与分红收益分开，缺失不填假数据 |
| `compute_fund_statistics` | 序列/代码、期间、收益口径、年化约定 | 累计/年化收益、波动、最大回撤、回撤区间、有效样本数和覆盖期；算法版本及假设 |
| `compare_funds` | 多代码、共同期间、共同口径 | 对齐交易日期后比较，拒绝把不同币种/分红口径无提示混比 |
| `get_data_source_health` | 能力/样本类型 | 传输、业务、数据有效性、时效、覆盖和授权状态分别报告 |

建议新的 snapshot 契约包含 `schema_version、provider、upstream_group、data_kind、value_basis、as_of、fetched_at、nav_date、currency、quality、method、missing_reason`。当前 `FundRealtimeData` 通过兼容字段承载本次修复，未来升级时保留旧 REST 适配，不直接破坏前端；新 CLI/MCP 则优先使用无歧义字段。

统计由确定性代码执行，模型只解释：

- 累计收益链乘一致口径日收益；年化按明确持有区间及约定，极短样本不给夸大年化。
- 波动率说明样本频率、有效点数、自由度与年化天数；不把 252 生硬应用所有海外/货币基金。
- 最大回撤输出峰值/谷值日期与恢复状态；历史缺口不能被当作平滑无风险收益。
- 对比分清 NAV 价格收益、来源增长率、分红再投总收益以及含现金流的组合收益；缺数据给出限制，不让模型心算补齐。
- 默认只读公共行情；持仓操作另设授权工具，不把 AI API 密钥或本地账户内容放进公共 tool result。

实施顺序与验收门槛：

1. **核心契约与回归**：解耦数据核心、统计算法和来源健康；覆盖旧接口失效、业务空响应、旧行情、官方收盘更新、分红、日期、货币基金和跨市场案例。完成条件是相同输入经核心与现 REST 得到同一选择和数值，而不是“新增几个类”。
2. **用户选定工具层后**：接入官方 MCP SDK 或 FastMCP 二者之一，先 stdio 本地只读工具，CLI JSON 为不支持 MCP 的宿主提供兼容路径；再评估受控 HTTP。采用结构化输出/schema，域级数据失败和协议错误分开。[MCP 工具输出规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)。
3. **薄 skill 与跨模型验收**：按官方 skill 格式分离说明/脚本/参考资料，不把供应商抓取逻辑复制进 skill。用至少两个不同模型、一个不支持 MCP 的工具宿主验证：新数据查询、主动基金缺估值、手动 NAV、历史统计、源失效与不可查询；只认可工具证据，不认可语言上“像是会查”。
4. **可维护性/误差评估**：按基金类型、开盘/午休/收盘/QDII 场景记录来源覆盖与推测误差；有真实缺口时再考虑授权源。持续监控/定时任务需要另行确认，本次没有创建自动化或承诺后台通知。
